# InsightHub – Static Code Analysis Observations

Scope: everything under `backend/`, `frontend/`, `shared/`, `docs/` and the Docker/compose setup, reviewed statically (nothing was run).
I grouped findings into **Backend / Frontend** × **Security / Code quality / Wrong (non-intuitive or wrongly implemented) feature**.

Severity: **C** = critical (exploitable now, cross-tenant or account takeover) · **H** = high · **M** = medium · **L** = low.
File references are `path:line` against the current `master`.

## 1. Backend – Security

### 1.1 Authentication & authorization

| Sev | Issue | Where | Recommendation |
|-----|-------|-------|----------------|
| C | **Token forgery.** `/verify` and `/refresh` call `jwt.decode()`, which skips signature checking. Craft `{userId: <victim>}` with no signature, call `/refresh`, and you get a properly signed JWT for the victim. User IDs leak through `/users/search` and `/users/:id`. | `routes/auth.ts:241, 281` | Use `jwt.verify` everywhere. Make `/refresh` require a separate refresh token (rotated and revocable). |
| C | **Auth middleware fails open.** In the `catch (jwtError)` branch it logs and calls `next()`. The request continues with `req.user === undefined`. Most handlers then crash on `req.user!` and return 500, and handlers that don't read `req.user` (billing `/webhook`, `/pricing`, webhooks `/incoming`, `/deliveries`) are fully reachable. The `!` non-null assertions hide the bug from TypeScript. | `middleware/auth.ts:57-60` | `return res.status(401)…`. Turn on `strict` TS and remove the `req.user!` assertions, for example with a typed `AuthenticatedRequest` produced by the middleware. |
| C | **Cross-tenant IDOR.** These endpoints fetch or modify by primary key without an `organizationId`/`userId` filter: `PUT/DELETE /organizations/members/:id` (`organizations.ts:195, 264`; the comment at 271 even admits it), `POST /transfer-ownership` new owner from any org (`:493`), `DELETE /api-keys/:id` (`:409`), `GET/PUT/DELETE /webhooks/:id` + `regenerate-secret` (`webhooks.ts:29, 91, 121, 138`; GET also leaks the HMAC secret), `GET /billing/invoices/:id` (`billing.ts:273`), `GET /users/:userId` (leaks `stripeCustomerId`, budget; `users.ts:133`), `GET /users/search/:q` searches **all** tenants (`users.ts:171`), `DELETE /users/me/sessions/:id` (`users.ts:224`), `PUT /notifications/:id/read` and `DELETE /notifications/:id` (`notifications.ts:51, 85`), `GET /audit/user/:userId` (`audit.ts:256`), widget update/delete/data where `widgetId` is never tied to the checked dashboard (`dashboard.ts:262, 292, 322`), and comments, which have no org at all (`comments.ts`, `schema.prisma:194`). | listed | Scope every query by tenant (`updateMany/deleteMany where {id, organizationId}`, or `findFirst` with org then act). Better: add a repository layer or Prisma client extension that injects `organizationId` automatically so new endpoints can't forget it. Add tenant-isolation integration tests. |
| H | **Privilege escalation via roles.** `/invite` accepts any `role`, so an admin can create owners (`organizations.ts:146`). `PUT /members/:id` lets an admin promote anyone, including themselves, to owner (`:224`). `PUT /organizations/current` lets an admin set `tier` with no payment (`:61`). | `routes/organizations.ts` | Validate role with zod and allow only owners to grant `owner`. Remove `tier` from the generic update so billing goes only through the billing flow. |
| H | **Missing RBAC.** Any member, including a *viewer*, can update/delete/share dashboards (`dashboard.ts:113,155,495`), delete all analytics events (the comment says "admin only" but there's no check; `analytics.ts:223`), broadcast notifications to the whole org (`notifications.ts:157`), read all audit logs with IPs/user agents (`audit.ts:10`), read webhook secrets (`webhooks.ts:12`), and record arbitrary or negative usage to lower spend (`billing.ts:96`). | listed | Define one permission matrix (shared with the frontend) and enforce it with `requireRole`/`requirePermission` on every mutating route. |
| H | **Logout/session revocation do nothing.** The JWT is stateless with a 7-day expiry, and `authMiddleware` never checks the `Session` table. Logout deletes sessions `where token = <JWT>`, but sessions store a separate random token, so nothing matches (`auth.ts:177`). | `routes/auth.ts:40-50,171-187`, `middleware/auth.ts` | Either check a session/`jti` on each request (backed by Redis) or use short-lived access tokens plus revocable refresh tokens. |
| H | **Transfer ownership never verifies the password** even though it requires one. | `routes/organizations.ts:479-499` | Verify the password. Require the new owner to be active and in the same org. Run it in a transaction with the audit log. |
| H | **Default password for invited users** (`ChangeMe123!`). It is hard-coded, logged in plain text and returned in the API response. | `routes/organizations.ts:137,162,182` | Use an invite token emailed to the user (single use, expiring) and have them set their own password. |
| M | Password reset is a stub: `/forgot-password` logs the token to stdout and `/reset-password` returns "success" without changing anything. | `routes/auth.ts:190-229` | Implement it (hashed token plus expiry) or remove the endpoints. Never log tokens. |
| M | Password policy is inconsistent (8 chars on register, 6 on change). Login reveals whether a user exists through timing (no hash computed when the user is missing). | `middleware/validate.ts:30`, `routes/users.ts:87`, `routes/auth.ts:21-27` | Use one shared zod schema. Compute a dummy hash when the user isn't found. |

### 1.2 Injection, crypto, secrets

| Sev | Issue | Where | Recommendation |
|-----|-------|-------|----------------|
| C | **SQL injection.** `getAnalyticsByFilter` (reachable from `GET /analytics/data?eventType=…`), `searchEvents` (`/analytics/search?q=`), `getAuditLogs` (`/audit?orderBy=` goes straight into `ORDER BY`), and `bulkInsertEvents` (`/analytics/track/batch`, event fields and JSON go into `VALUES`). | C | **MD5 password hashing** with no salt, plus a non-constant-time compare. `bcrypt` is already a dependency but unused. The seed uses MD5 too. | `utils/encryption.ts:33-39`, `prisma/seed.ts:6` | Use bcrypt or argon2, and rehash legacy MD5 hashes on the next successful login. |
| C | **`passwordHash` returned from `/auth/login`.** | `routes/auth.ts:67` | Remove it. Return a DTO built from an explicit allowlist. |
| H | **Hard-coded secrets.** JWT secret fallback `'super-secret-key-change-in-production'` (also in `docker-compose.yml`). | H | **SSRF through webhooks.** Any URL is accepted (`http://169.254.169.254`, `http://postgres:5432`, `localhost`…), and `/test` returns the first 500 bytes of the response to the caller. | `routes/webhooks.ts:47-51, 201-254` | Allow only `https` and resolve DNS at delivery time, blocking private/link-local/loopback ranges. | H | **Stripe webhook has no signature verification.** Anyone could mark invoices paid if it were reachable. It is also mounted behind JWT auth (see §3). | `routes/billing.ts:289` | Use `stripe.webhooks.constructEvent` with the raw body, mounted outside the JWT router. |

| H | **CORS** `origin: '*'` together with `credentials: true`. | `index.ts:27-30` | Use an explicit origin allowlist from config. |
| M | **API keys stored in plain text.** Lookup is by plaintext `key` and `GET /api-keys` returns the full key. `keyHash` is computed but never used. | `routes/organizations.ts:330, 369`, `middleware/auth.ts:104` | Store only the hash plus a display prefix, and look up by hash. |
| M | **Sensitive data in logs:** full API keys (`auth.ts:135`, `organizations.ts:377`), card token (`billing.ts:349`), reset token, default password, webhook bodies (`webhooks.ts:314`), preferences. `maskSensitiveData` logs the payload it is supposed to mask. | various | Use a structured logger (`winston` is already a dependency) with redaction. |
| M | **Global error handler leaks `err.message` and `err.stack`** to clients. | `index.ts:95-102` | Return a generic message plus a correlation ID, and log details server-side only. |
| M | **HTML injection in emails.** User-controlled `name`, org name, and notification title/message are interpolated into HTML. | `jobs/notifications.ts:93-98, 131-142, 167-178` | Escape the values or use a templating engine with auto-escaping. |
| M | **Unused path-traversal helpers.** `readExportFile` and `deleteExport` take arbitrary paths, and `listExports` returns every org's files. | `utils/export.ts:67-89` | Delete them, or constrain them to `EXPORT_DIR` + an org prefix with `path.resolve` checks. |
| M | **Rate limiter.** It is in-memory and per process. Without `app.set('trust proxy')` behind a proxy, all clients share one IP (or one client can bypass it). The `auth` limiter shares the same map. `express-rate-limit` is already a dependency. | `middleware/rateLimit.ts` | Use `express-rate-limit` with a Redis store and configure `trust proxy`. |
| M | **No input validation on most routes.** Zod schemas exist (`analyticsEventSchema`, `updateUserSchema`, `paginationSchema`, `validateQuery`) but are unused. `/track/batch` accepts an unbounded array. Free-form JSON is accepted for `settings` and `config`. | `middleware/validate.ts` | Validate body, query and params on every route, and cap batch size. |

## 7. Suggested remediation order

1. **Stop the bleeding (security, about 1 day).** `jwt.verify` in verify/refresh, fail-closed middleware, parameterize or remove raw SQL, add tenant scoping to every by-ID query, authenticate the WebSocket, stop returning `passwordHash`, bcrypt with rehash-on-login, required secrets, SSRF guard, CORS allowlist, no stack traces.
2. **Make authorization explicit.** One permission matrix in `shared/`, enforced by middleware on every route and mirrored (cosmetically) in the UI. Lock down role grants, tier changes and usage endpoints.
3. **Tests that matter.** Supertest integration suite with a real Postgres, starting with "org A cannot touch org B" for every route plus auth edge cases. Delete the mock-only tests.
4. **Frontend state.** React Query as the only server-state store, immutable Zustand for UI state, session bootstrap on load, cache clearing on logout, one WS connection that drives query invalidation.
5. **Fix the API contract.** Shared zod schemas and types for requests and responses, then fix every mismatch in §6.
6. **Operational hardening.** Redis-backed cache and rate limiting, a queue for jobs, emails and webhooks (idempotent, locked), indexes, pagination and streaming exports, `Decimal` for money, transactions.
